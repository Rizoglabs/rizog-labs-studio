# RizogKey Protocol V1

Status: Draft for implementation  
Owner: Rizog Labs Studio  
Scope: Internal licensing infrastructure for Rizog Labs applications

## 1. Purpose

RizogKey is the internal licensing infrastructure used by Rizog Labs applications.

Rizog Labs Studio is the administrative control center. RizogKey Client is the application-side licensing component embedded into customer applications.

Customer-facing applications must use neutral terms such as:
- Installation Code
- Activation Code
- License
- Activation

The name "RizogKey" is an internal implementation/infrastructure term and must not be exposed as a customer-facing brand.

## 2. Architecture

```
Rizog Labs Studio
  └── Activation Generator / History / Revoke
               │
               ▼
       RizogKey Licensing API
               │
               ▼
          Supabase
               ▲
               │
       RizogKey Client
        ┌──────┴──────┐
        ▼             ▼
 Android Adapter   Web Adapter
        │             │
        ▼             ▼
     RupKas        Other Apps
```

The server is authoritative for license state. The client maintains a signed local license grant so an activated application can continue to operate during the approved offline grace period.

## 3. Core Objects

### 3.1 Product

Identifies an application sold by Rizog Labs.

Required:
- product_id
- product_code
- product_name
- status

Example:
- product_code: RUPKAS
- product_name: RupKas

### 3.2 Installation

Identifies one application installation.

Required:
- installation_id
- product_id
- public_key
- platform
- created_at
- last_seen_at
- status

The installation identity is generated by RizogKey Client.

### 3.3 Activation Code

A one-time server-generated code issued by Rizog Labs.

Required:
- activation_code_hash
- product_id
- customer_name
- duration_code
- device_limit
- generated_at
- status

The raw activation code is returned only during successful generation and must not be stored in plaintext.

### 3.4 License

Represents the active entitlement resulting from successful activation.

Required:
- license_id
- product_id
- installation_id
- customer/reference metadata
- duration_code
- activated_at
- expires_at (null for lifetime)
- device_limit
- status
- last_validated_at
- created_at
- updated_at

### 3.5 License Event

Immutable audit record.

Event types:
- ACTIVATED
- VALIDATED
- REVALIDATED
- REVOKED
- EXPIRED
- TRANSFERRED
- INSTALLATION_REVOKED

## 4. License State Machine

Server-side license states:

```
PENDING
  │
  ▼
ACTIVE ───────────────► REVOKED
  │
  └───────────────────► EXPIRED

REVOKED / EXPIRED
  └── cannot automatically return to ACTIVE
```

A new device transfer uses a new installation and a new activation code.

An Activation Code is one-time use. It must never be accepted twice.

## 5. Installation Identity

### Android

Use an application-generated installation identity backed by an Android Keystore key pair where supported.

- Private key remains on device.
- Public key is registered with the licensing service.
- Signing/verification can prove possession of the installation key without transmitting the private key.

### Web

Use Web Crypto plus browser-persistent storage appropriate to the application.

Web storage is not a permanent hardware identity. Web licensing must therefore rely more heavily on server-side session/revalidation controls.

## 6. Activation Flow

### Step A — First launch

1. Application initializes RizogKey Client.
2. Client creates installation identity if none exists.
3. Client produces an Installation Code representation.
4. Application shows the Installation Code to the customer.
5. License state is UNACTIVATED.

### Step B — Rizog Labs generates Activation Code

Admin enters:
- Product
- Customer Name
- Installation Code
- Duration
- Device Limit

Rizog Labs Studio calls the server-side generation function.

### Step C — Customer activates

Client sends an activation request containing:
- product_id
- installation_id
- activation_code
- platform
- client_version
- installation public key
- proof of possession/signature when supported

Server validates:
1. authenticated/request integrity rules
2. product
3. activation code
4. activation code unused status
5. installation binding
6. device limit
7. duration
8. license conflict
9. revoked/expired conditions

On success:
- activation code becomes USED
- license becomes ACTIVE
- activation time is recorded
- expiration is calculated from activation time
- license grant is generated
- ACTIVATED event is recorded

## 7. License Grant

The client must receive a signed license grant rather than an unauthenticated boolean.

Conceptual payload:

```json
{
  "version": 1,
  "license_id": "LIC-...",
  "product_code": "RUPKAS",
  "installation_id": "INST-...",
  "status": "ACTIVE",
  "activated_at": "2026-10-05T00:00:00Z",
  "expires_at": "2027-10-05T00:00:00Z",
  "device_limit": 1,
  "offline_until": "2027-01-03T00:00:00Z",
  "issued_at": "2026-10-05T00:00:00Z"
}
```

The production implementation should use a server signature so the client can detect tampering.


## 7A. Signed Grant Canonicalization and Trust

License Grant signatures use a deterministic canonical JSON serialization for the V1 signing payload:

- object keys are sorted lexicographically;
- arrays preserve their existing order;
- primitive values use JSON serialization;
- whitespace is not added.

The signature is calculated over the UTF-8 bytes of the canonical Grant JSON.

Clients must verify the signature against a locally trusted signing-key map keyed by `key_version`. A client must NOT trust a public key merely because the server returned it beside the signature.

Signing-key rotation is represented by a new `key_version`. Applications may ship more than one trusted public key during a rotation window.

## 8. Local License State

Client may cache the latest valid grant locally.

Client must store enough state to determine:
- whether activation exists
- license status
- expiration
- last successful validation
- offline grace boundary
- product binding
- installation binding

The client must not store server secrets.

## 9. Offline Behavior

After initial activation, application use is allowed offline until the configured offline grace boundary.

Recommended initial V1 policy:

- Activation requires online validation.
- Normal operation may continue offline.
- Revalidation is attempted when connectivity is available.
- Default offline grace target: 90 days.
- Grace period must be server-issued and represented in the signed grant.
- If the grace boundary is exceeded, application enters LICENSE_REVALIDATION_REQUIRED.

The grace duration should remain configurable server-side.

## 10. Revalidation

A client should revalidate:
- on a periodic schedule
- when the app returns online
- when the local grant approaches its grace boundary
- after a meaningful application update when required

Successful revalidation:
- updates last_validated_at
- issues an updated signed grant
- records REVALIDATED

Failed revalidation must distinguish:
- network unavailable
- temporary server failure
- license invalid
- license revoked
- license expired

Network failure alone must not immediately lock a valid offline installation.

## 11. Revoke

Rizog Labs Studio may revoke a license.

Server:
- sets license status to REVOKED
- records revoked_at
- records revoked_by
- records reason
- writes REVOKED event

Client:
- continues according to the last valid offline grant until server contact is possible
- on successful revalidation, detects REVOKED
- transitions to LICENSE_REVOKED
- shows application-specific activation/support UI

## 12. Device Transfer

Transfer flow:

```
Old Installation
      │
      ▼
License revoked
      │
      ▼
New installation created
      │
      ▼
New activation code generated
      │
      ▼
New license activated
```

An old installation must not be silently migrated to a new installation without an explicit server-side operation.

## 13. API Contract

Initial logical endpoints/actions:

### POST /license/activate

Request:

```json
{
  "product_code": "RUPKAS",
  "installation_id": "INST-...",
  "activation_code": "RPK-...",
  "platform": "android",
  "client_version": "1.0.0",
  "public_key": "..."
}
```

Response:

```json
{
  "ok": true,
  "license_grant": {
    "version": 1,
    "license_id": "LIC-...",
    "product_code": "RUPKAS",
    "installation_id": "INST-...",
    "status": "ACTIVE",
    "activated_at": "...",
    "expires_at": "...",
    "device_limit": 1,
    "offline_until": "..."
  },
  "signature": "..."
}
```

### POST /license/revalidate

Request:

```json
{
  "product_code": "RUPKAS",
  "installation_id": "INST-...",
  "license_id": "LIC-...",
  "client_version": "1.0.0",
  "public_key": "..."
}
```

Response:
- current authoritative license state
- refreshed signed license grant when valid

### POST /license/register-installation

Registers a new installation identity before activation when required by the server flow.

### Admin actions

Admin-only operations remain behind Rizog Labs Studio / server-side privileged functions:
- generate activation
- list history
- revoke license
- register/approve transfer

Customer applications must never receive admin privileges.

## 14. Client API

The reusable RizogKey Client should expose a small stable interface.

Conceptual API:

```ts
RizogKey.initialize(config)

RizogKey.getInstallationCode()

RizogKey.getStatus()

RizogKey.activate(activationCode)

RizogKey.revalidate()

RizogKey.isActive()

RizogKey.isExpired()

RizogKey.getLicense()

RizogKey.clearLocalState()
```

Application business logic should depend on this interface, not on Supabase directly.

- RK_ACTIVATION_REQUIRED
- RK_ACTIVATION_INVALID
- RK_ACTIVATION_USED
- RK_PRODUCT_MISMATCH
- RK_DEVICE_LIMIT
- RK_LICENSE_REVOKED
- RK_LICENSE_EXPIRED
- RK_REVALIDATION_REQUIRED
- RK_NETWORK_UNAVAILABLE

The application can map these to human-readable Indonesian messages.

## 16. Security Rules

1. No service-role key in any client.
2. No Supabase secret in any client.
3. Activation generation stays server-side.
4. Activation codes are stored as hashes.
5. Raw Activation Codes are returned only on successful generation.
6. License grants are signed.
7. Private installation keys remain on device.
8. License state is authoritative on the server.
9. Client must verify the grant signature.
10. Revoke is authoritative after successful server contact.
11. Device transfer requires an explicit server-side operation.
12. Do not depend on obscurity alone.
13. Client code should assume it can be inspected or modified.
14. Business-critical authorization remains server-controlled.

## 17. Product Integration Contract

Every Rizog Labs application integrating RizogKey must define:

- product_code
- minimum supported RizogKey protocol version
- client version
- platform
- application response for UNACTIVATED
- application response for REVOKED
- application response for EXPIRED
- application response for REVALIDATION_REQUIRED

Example:

```text
Application: RupKas
Product Code: RUPKAS
Protocol: RizogKey V1
Platform: Android / Web
```

## 18. Compatibility

Protocol version is independent from application version.

Example:

```
RizogKey Protocol V1
  ├── RupKas 1.0
  ├── RupKas 1.1
  └── Other App 1.0
```

Breaking changes require a new protocol version.

Non-breaking fields may be added using explicit versioning and backward-compatible parsing.

## 19. V1 Acceptance Criteria

RizogKey Protocol V1 is considered implementation-ready when:

- A new installation can create a unique installation identity.
- A valid one-time Activation Code can activate exactly one permitted installation.
- Activation begins the license duration.
- Device limit is enforced server-side.
- A signed license grant is issued.
- The client can validate a grant locally.
- The client can operate within the configured offline grace window.
- Revalidation refreshes a valid license.
- Revoke is detected after server contact.
- Expired licenses are detected.
- Device transfer requires an explicit new activation.
- No server secret is present in client code.
- Audit events exist for activation, validation/revalidation, revoke, expiry and transfer.
- RupKas can consume the Client API without directly implementing license business rules.

## 20. Implementation Sequence

1. Freeze this protocol.
2. Extend Supabase schema with installations, licenses and license_events.
3. Implement server-side activation/revalidation/installation operations.
4. Implement signed license grants.
5. Build RizogKey Core.
6. Build Android Adapter.
7. Build Web Adapter.
8. Build a small RizogKey Test App.
9. Integrate into RupKas.
10. Run activation, offline, expiry, revoke and transfer test matrices.
11. Tag the first stable RizogKey Client release.

## 21. Non-Goals for V1

The following are intentionally outside this protocol version:
- automatic subscription billing
- customer self-service licensing portal
- advanced anti-debug/anti-tamper protection
- hardware fingerprinting as the sole identity mechanism
- DRM-style protection
- SaaS licensing for external companies
- automatic license transfer without admin approval
